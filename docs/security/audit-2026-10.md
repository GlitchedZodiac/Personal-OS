## Finding details (material findings)

### SEC-001 — Cookie-signing secret derives from the PIN when `AUTH_COOKIE_SECRET` is unset

- **Severity:** Critical — a stranger can forge a valid `auth` cookie.
- **Door:** `lib/auth.ts` (`getCookieSecret`), `proxy.ts`.
- **What happens:** `getCookieSecret()` is
  `sha256((AUTH_COOKIE_SECRET || APP_PIN) + ":personal-os:auth-cookie")`.
  When `AUTH_COOKIE_SECRET` is unset, the whole secret is a pure function of a
  4–8 digit PIN. The cookie is `base64url(JSON).HMAC`. An attacker who seeds
  a candidate PIN re-derives the secret and signs a token for
  `sub:"personal-os"`; `verifyAuthToken` accepts it. The proxy applies **no**
  rate limit to `/api/*`, so candidate cookies can be tried online at line
  speed, or — once any valid cookie is observed — the PIN is recovered
  offline in milliseconds. 10^4–10^8 candidates is trivial.
- **Reproduction (script, 2026-10-17):** a vitest file imports the real
  `createAuthToken`/`verifyAuthToken`, sets `APP_PIN` with
  `AUTH_COOKIE_SECRET` unset, and shows (a) a token forged from the PIN is
  accepted, (b) a token forged from a wrong PIN is rejected (the oracle),
  (c) with a strong `AUTH_COOKIE_SECRET` the PIN-derived forgery fails. All
  assertions pass.
- **Fix (planned, batch auth/cookie):** in production, refuse to mint or
  verify cookies unless `AUTH_COOKIE_SECRET` is set and ≥32 chars — a clear
  503 on `/api/auth` and a log line naming the variable; never a silent
  degrade to the PIN. Derive per-purpose subkeys from it. Dev keeps working
  with a loud warning.
- **Rating is conditional:** whether `AUTH_COOKIE_SECRET` is set in Vercel is
  **unverified** from this lane. When both it and `APP_AUTH_SECRET` are unset,
  SEC-002 dominates (it yields the PIN outright); SEC-001 matters alone only
  when `APP_AUTH_SECRET` is set and this one is not.
- **Fix (3a, as shipped):** `scripts/security-preflight.mjs` fails a
  production build without a 32+-char value (first line — the previous
  deployment stays live); at runtime production refuses to sign or verify and
  `/api/auth` answers 503 naming the variable (second line).
- **Michael:** set `AUTH_COOKIE_SECRET` (≥32 characters, `openssl rand -hex 32`)
  in Vercel Production + Preview **before merging**.

### SEC-002 — App secret falls back to the PIN; the public DCR endpoint is an offline PIN oracle

- **Severity:** Critical — the PIN is recoverable with no credential at all.
- **Door:** `lib/security.ts` (`getAppSecret`), `/api/oauth/register`,
  `lib/oauth.ts` (`mintDcrClientId`/`signCompact`).
- **What happens:** `getAppSecret()` is
  `APP_AUTH_SECRET || NEXTAUTH_SECRET || APP_PIN || "personal-os-local-secret"`.
  It keys the PIN hash, every device/refresh/OAuth-code token hash, and the
  HMAC on stateless DCR client ids. `/api/oauth/register` is public
  (allowlisted) and unauthenticated; it returns
  `client_id = "pos1." + base64url(payload) + "." + HMAC(payload, appSecret)`.
  With `APP_AUTH_SECRET`/`NEXTAUTH_SECRET` unset, the HMAC key is the PIN, so
  a single `register` call hands an attacker a known plaintext + its MAC.
  They enumerate PINs offline until the MAC matches — then they know the PIN,
  can log in, forge cookies (SEC-001), mint device/MCP sessions, and recompute
  the PIN hash (SEC-003).
- **Reproduction (local, 2026-10-17):** `POST /api/oauth/register` with a
  claude.ai redirect returned a `client_id`; an offline loop over candidate
  PINs recomputed `HMAC(payload, pin)` and matched the signature, recovering
  the configured PIN (4 digits). A control with a strong `APP_AUTH_SECRET`
  recovered nothing. **Run against the local server only.**
- **Fix (planned, batch auth/cookie):** same fail-closed requirement for
  `APP_AUTH_SECRET` in production; per-purpose subkeys so the DCR MAC key is
  not the login key.
- **Scope correction (review):** device/connector tokens are 256-bit random
  values; the app secret only keys their lookup hash. Recovering it yields
  the PIN, the cookie (via SEC-001) and the ability to mint NEW sessions by
  logging in — not the forgery of existing tokens.
- **Rating is conditional:** whether `APP_AUTH_SECRET` or `NEXTAUTH_SECRET` is
  set in Vercel is **unverified** from this lane.
- **Fix (3a, as shipped):** production throws `MissingSecretError` (the
  message names the variable) wherever a key is needed, instead of deriving
  from the PIN; keys are derived per purpose; the preflight fails the
  production build first. Legacy hashes are recognised through 2027-01-17
  across every candidate of the old chain, including a leftover
  `NEXTAUTH_SECRET` (`tests/mobile-session-legacy.test.ts`).
- **Michael:** set `APP_AUTH_SECRET` (≥32 characters, `openssl rand -hex 32`)
  in Vercel Production + Preview **before merging**.

### SEC-065 — The literal "1234" was a valid pairing PIN when `APP_PIN` was unset

### SEC-004 — A PIN change is not durable and never reaches device pairing

- **Severity:** High.
- **Door:** `/api/auth/update-pin`, `lib/pin-auth.ts`, `lib/auth.ts`.
- **What happens:** `update-pin` writes `.env.local` (read-only on Vercel —
  a silent no-op there) and `process.env.APP_PIN` on the one warm instance
  (lost on the next cold start). It never writes `auth_credentials.pinHash`.
  Device pairing (`lib/pin-auth.verifyPin`) checks that DB row first; once it
  exists (created on the first fallback pairing) it keeps accepting the **old**
  PIN after a "change", while the web login reverts to the old env PIN on the
  next cold start. A changed PIN is therefore neither durable nor complete.
- **Reproduction (trace):** read the three files; `update-pin` has no
  `prisma.authCredential` write; `verifyPin` prefers the stored hash.
- **Fix (3a):** `auth_credentials.pinHash` (scrypt) is the single source for
  the web login and pairing; `APP_PIN` only seeds a missing row (plus a
  one-time re-seed while the row is still in the legacy format, because web
  and pairing may disagree today — D9a); the `.env.local` writer is deleted;
  `update-pin` is cookie-gated (SEC-009). Live on :3101: a PIN change was
  followed by both the web login and device pairing, and the old PIN was
  refused by both.

### SEC-010 / SEC-011 — Any device token reaches the MCP surface, including finance and spirit

- **Severity:** High.
- **Door:** `/api/mcp`, `lib/mobile-session.ts`, `lib/mcp/tools.ts`,
  `lib/ai/data-registry.ts`.
- **What happens:** `/api/mcp` authenticates with `requireMobileSession`,
  which matches only `tokenHash`/`revokedAt`/`expiresAt` — `deviceType` is
  never checked (the code comment says "any valid device session is
  accepted"). So a watch or phone token (30/90-day, lives on a device that can
  be lost) opens the full 26-tool connector. `query_data` has no per-token
  scope: `finance_accounts`, `finance_transactions`, `finance_budgets`,
  `spirit_notes`, `journal` and more are in the registry and absent from
  `EXCLUDED_MODELS`, and `executeAppData` takes no scope argument. One leaked
  wrist token reads his money and his faith notes and can drive the
  destructive tools.
- **Reproduction (script):** a watch-typed session passes
  `requireMobileSession` via both `Authorization: Bearer` and `x-api-key`
  (SEC-019); the lookup WHERE has no `deviceType`; the registry exposes the
  finance/spirit datasets and their models are not excluded; `executeAppData`
  has arity ≤2 (args, ctx) — no token/scope parameter.
- **Fix (planned, batch MCP+OAuth):** require `deviceType==="mcp"` at
  `/api/mcp` (D4); default-deny `finance_*` over MCP behind a Settings toggle
  (D3).

### SEC-038 — Three cron routes fail open when `CRON_SECRET` is unset

- **Severity:** High if `CRON_SECRET` is unset in production; Low otherwise.
- **Door:** `/api/cron/daily-refresh`, `/finance-sync`, `/spirit-reminder`
  (and the four others compare non-constant-time).
- **What happens:** the guard is
  `if (process.env.CRON_SECRET && authHeader !== "Bearer " + process.env.CRON_SECRET) 401`.
  When `CRON_SECRET` is unset the left side is falsy, so the route runs for
  anyone. These trigger Gmail finance sync, the daily refresh, and the spirit
  push. The other four (`reminder-push`, `renpho-sync`, `training-nudge`,
  `weekly-report`) use `!process.env.CRON_SECRET || …`, which fails closed,
  but all seven use `!==` rather than a timing-safe compare.
- **Reproduction (script + trace):** the guard expression evaluates to
  "not blocked" when `CRON_SECRET` is unset; grep confirms three routes use
  the fail-open shape.
- **Severity note (review):** Medium, not High — an unset `CRON_SECRET` would
  also have 401'd `reminder-push` (24 schedules) and `weekly-report`, which
  he would have noticed within a day; the open routes expose counts and the
  timezone, not his data.
- **Fix (3a):** one shared `requireCronSecret()` (`lib/cron-auth.ts`) that
  refuses when the secret is unset, compares in constant time and logs the
  missing variable; all seven crons use it and `secretEquals` guards the
  admin route. `tests/cron-auth.test.ts` also fails if any cron file stops
  importing it.

### SEC-005 — Login/pairing rate limit is bypassable and per-instance

- **Severity:** Medium.
- **Door:** `lib/auth.ts` (`checkRateLimit`, `getClientIdentifier`).
- **What happens:** the limiter is a module-level `Map` keyed on the first
  `x-forwarded-for` value. The client controls that header, so rotating it
  resets the bucket; and on serverless the map is per warm instance, so
  attempts spread across instances for free. It does not meaningfully limit
  PIN guessing — which matters most for `/api/mobile/auth/session` (pairing)
  and, combined with SEC-001, for cookie forgery.
- **Reproduction (script):** five failures block one IP; a different
  `x-forwarded-for` is immediately allowed again.
- **Qualification (review):** Vercel's edge overwrites `x-forwarded-for` with
  the connecting IP, so the header-rotation bypass holds locally but almost
  certainly not on Vercel; the per-instance memory is the real issue.
- **Fix (3a):** `x-real-ip` is preferred, and a GLOBAL per-scope cap (50
  failures in an hour from anyone locks the scope and logs) defeats rotation
  on a single instance. **3b:** cap/window from env; a client with no wrong
  guesses of its own may still present the CORRECT PIN during a lock (so a
  flood cannot lock Michael out); tripping the lock raises a `systemAlerts`
  notification. **Residual:** during a lock each fresh IP gets one real PIN
  check (~50 + one per fresh IP per window). **3c (D2 + D2b):** a DB-backed
  bucket shared across instances, and the exemption narrowed to a signed
  known-device marker so fresh IPs get nothing during a lock.

### SEC-028 / SEC-053 — Progress photos: untyped unbounded upload, blob-heavy list, crashing limit

- **Severity:** Medium.
- **Door:** `/api/health/progress-photos`.
- **What happens:** POST stores any string as `imageData` with no type or
  size check. GET runs `findMany` with no `select`, so the full base64 image
  rides every row of the list response (`limit` up to whatever is sent).
  `limit` is `parseInt(...)` with no clamp, so `?limit=abc` becomes
  `take: NaN` and the query throws (a 500 DoS primitive).
- **Reproduction (script):** a non-image string is stored and returned;
  the GET args carry no `select`; `limit=abc` yields `take:NaN`.
- **Fix (planned, batch uploads+bounds):** require a `data:image/` prefix and
  a size cap on POST; a `clampInt` on `limit`; a list projection that omits
  `imageData` (a thumbnail or id only).

### SEC-035 / SEC-036 — Strava tokens and the OpenAI admin key are plaintext at rest

- **Severity:** Medium.
- **Door:** `strava_tokens`, `integration_secrets`, `lib/strava.ts`,
  `/api/ai/admin-key`.
- **What happens:** Google finance tokens are AES-256-GCM in the vault, but
  Strava's access+refresh tokens and the OpenAI **org admin** key are stored
  raw. A database read (backup, snapshot, or a future query bug) exposes a
  live Strava grant and a billing-scoped OpenAI key.
- **Reproduction (trace):** the callback writes `data.access_token` straight
  to the column; `admin-key` upserts `value: key` raw.
- **Fix (planned, batch logging+deps+secrets):** encrypt both with the
  existing vault primitive, with a read-plaintext fallback that rewrites on
  the next refresh/save (D6). Needs `FINANCE_VAULT_MASTER_KEY` set in prod
  (it is, locally).

### SEC-059 — No security headers

- **Severity:** Medium.
- **Door:** `next.config.ts` (no `headers()`).
- **What happens:** production responses carry only Vercel's HSTS. No
  `X-Frame-Options`/`frame-ancestors` (the PIN screen and the app can be
  framed — clickjacking), no `X-Content-Type-Options: nosniff` (served blobs
  and the arbitrary-content-type recording segments, SEC-030, can be sniffed),
  no `Referrer-Policy` (the `/oauth/authorize?...code_challenge=...` URL can
  leak via Referer), no `Permissions-Policy`.
- **Reproduction (prod-readonly + local):** `curl -D-` on `/` and `/dashboard`
  shows none of these headers.
- **Fix (planned, batch headers+deployment):** `headers()` adding `nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`,
  `Permissions-Policy`, and `Content-Security-Policy: frame-ancestors 'none'`
  (the one CSP directive safe to ship without device testing; a full CSP is
  D5).
